# AGENTS.md

Instructions for AI coding agents working in this repository.

## Project

Next Frame — a small, deterministic anime recommendation app powered by the
AniList API. The user picks three distinct anime and receives one SFW,
discovery-first recommendation based on eligible related titles, community
recommendations, and metadata similarity. React 19 + TypeScript + Vite
frontend; no backend, database, accounts, or AI service. All state is
in-memory.

## Tech stack

- TypeScript 5.8 (strict), ESM-only (`"type": "module"`)
- Vite 6 (dev + build), Vitest 3 (tests, node environment)
- React 19 — the only runtime dependency; everything else is a devDependency
- ESLint 9 (flat config) and Prettier 3

## Package manager

- **Always use pnpm. Never use npm, yarn, or bun** — for install, scripts, or
  any executable.
- Correct: `pnpm install`, `pnpm dev`, `pnpm test`, `pnpm build`
- Use `pnpm exec` / `pnpm dlx` instead of `npx`.
- Never hand-edit `pnpm-lock.yaml` or `pnpm-workspace.yaml`.

## Commands

- `pnpm install` — install dependencies
- `pnpm dev` — start the Vite dev server
- `pnpm test` — run the test suite once (`vitest run`)
- `pnpm test:watch` — watch mode
- `pnpm lint` / `pnpm lint:fix` — ESLint
- `pnpm format` / `pnpm format:check` — Prettier
- `pnpm typecheck` — `tsc --noEmit`
- `pnpm build` — type-check then build to `dist/`
- `pnpm check` — lint, format check, tests and build in one command

## Restrictions

- Never edit `dist/` — it is generated by `pnpm build`.
- Never add runtime dependencies without explicit approval; React is the
  single approved exception. Dev-only tooling (linters, formatters, test
  helpers) also needs approval.
- Never introduce randomness into scoring; recommendations must be
  deterministic for identical inputs.
- Never persist state (no localStorage, cookies, IndexedDB) — selections
  stay in memory only.
- Never expose raw API errors to users; show friendly messages instead.
- No backend, database, auth, or LLM — the recommender stays a deterministic
  frontend.

## Code style

- Strict TypeScript: `noUnusedLocals` / `noUnusedParameters`,
  `noUncheckedIndexedAccess`, `verbatimModuleSyntax` — no dead code and
  no unchecked index access.
- Colocate tests as `*.test.ts` / `*.test.tsx` next to source under
  `src/`. One test file per source module — no grab-bag files.
- API calls only in `src/api/`; recommendation logic must never fetch.
- No DOM globals (`window`, `document`) outside `src/ui/` and
  `src/main.tsx`. The API and recommendation layers stay platform-neutral.
- `src/models/` holds all shared types (e.g. `UiState`); components import
  types, they do not declare them.
- Scoring weights and tunable numbers live in a `config.ts` module —
  configurable, not hardcoded.
- Use the `@` alias for cross-directory `src/` imports; same-directory
  imports may stay relative.
- Do not introduce unnecessary code comments. Comment a non-obvious
  constraint or a bug that was fixed, not what the code plainly does.
- No `console.log` in `src/`; surface state through the `UiState` union.
- Never weaken a `tsconfig.json` strict flag or silence an ESLint rule to
  make a build pass. Fix the code, or scope the rule off in
  `eslint.config.js` with a stated reason.

## Testing

- Never call the AniList API from tests; tests use fixture data or a
  mocked module boundary.
- Mock network boundaries with realistic shapes. A `Map` is not a stand-in
  for `Headers` — a `Map.get` returns `undefined` where a real one returns
  `null`, which silently hides header-handling bugs.
- Use fake timers for anything involving retry, backoff or debounce.
- Reset module state in `beforeEach`, and pair `vi.stubGlobal` with
  `vi.unstubAllGlobals()` in `afterEach`.
- Assert behavior, not implementation. Never assert on GraphQL document
  text or raw query strings.
- Determinism is a tested property, not just a claim: shuffle the inputs
  and assert identical output.
- When fixing a bug, add the regression test in the same change, and
  confirm it fails against the old code before trusting it.

## Changelog

- Maintain `CHANGELOG.md` using the
  [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format.
- Add every user-visible change (features, fixes, breaking changes,
  notable doc/tooling changes) under `## [Unreleased]` with
  `Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` subsections.
- Never edit released version sections; only append new entries.

## Before declaring work done

- `pnpm check` passes (lint, format, tests, build)
- `CHANGELOG.md` has an entry under `## [Unreleased]`, in Keep a Changelog
  order: `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed` — one
  section each, no duplicates
